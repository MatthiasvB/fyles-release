# Wire Protocol & API Contract

> **Parent:** [Architecture Overview](../ARCHITECTURE.md)

## 1. Contract-First Design

The entire client-service interface is defined in `.proto` files in the shared `wire/` directory.
Code is generated into both technology stacks:

| Stack | Generator | Output |
|-------|-----------|--------|
| Rust backend | `tonic-build` + `prost` | Server stubs + message types |
| Dart frontend | `protoc` + `grpc` plugin | `*.pb.dart`, `*.pbgrpc.dart`, `*.pbenum.dart` |

Neither output is committed. The Rust code is generated by each crate's `build.rs` at build time.
The Dart code in `fyles/lib/wire/` is generated by `generate_protos.sh`, which `setup_repo.sh`
runs, with the `protoc_plugin` version pinned in `fyles/pubspec.lock`.

Client and service ship together, so most messages need no backward compatibility. The exception
is `filerequest_compat.proto`: its messages travel between devices through QR codes and pastes,
so a device can read one that a different version wrote. Their field numbers are never reused,
and removed ones are reserved.

### Design Philosophy (from `filerequest.proto`)

```protobuf
// - No implicitly optional parameters in request messages
// - Each endpoint should have exactly one clear purpose
// - Split endpoints instead of using optional parameters
```

## 2. The stream is the state channel

Desktop runs one daemon and any number of client windows. A request/response mutation only
informs the window that made it, so **client state is not derived from replies**. It is derived
from the `ServerMessage` push stream, which reaches every attached window equally.

```protobuf
rpc Stream (stream ClientMessage) returns (stream ServerMessage);
```

Consequences that hold across the whole surface:

- The service pushes on **every** change to observable state, whether it originated in this
  window, another window on this device, or a sync from another device. The originating window is
  not a special case.
- `AppBloc` mutation handlers emit no state of their own. A handler that patched state locally
  would race the push and, worse, hide a push that was never implemented.
- Everything a window can render therefore needs a push for every way that state can change.
  `core/src/core/brain/client_push.rs` is where that coverage lives. Auditing it against the
  `ServerMessage` oneof is how you check for gaps.

### Three push shapes

**Scoped entity** (`ContactUpserted`, `FilerequestRemoved`, `PendingFilesAdded`, …) carries the one
thing that changed, and the client patches its copy by key. This is what a local write emits: the
handler already holds the entity it just wrote, so the push costs no read and puts no unrelated
window's data on the wire. It matches what the RPC's own response would have carried.

**Full state** (`ContactsChanged`, `RemoteFilerequestsChanged`, `OwnedDevicesChanged`) carries a
whole concern and the client replaces its copy outright. Reserved for sync convergence, where the
changed set is genuinely unknown: a merge with another device reports that the document moved, not
which entries moved with it. `SelfContactChanged`, `SettingsChanged` and `ListenStatusChanged` are
whole-concern too, but only because the concern is a single value.

**Scoped signal** (`ReceivedFilesChanged`) names what changed and lets the client re-read just
that. Used where full state would be large and per-key: received-file lists are per-filerequest
and can be long.

Progress stays a **delta** (`PendingFileStatusChanged`, `ReceivedFileStatusChanged`). Transfer
progress is emitted per 512 KB chunk, so it must never trigger a list read. The deltas carry only
live transfer state. Whether a file belongs in a list is answered separately by the messages
above.

### Ordering

Handlers emit the push *before* answering the request that caused it. gRPC gives no ordering
guarantee between a unary reply and the stream, but since no state rides on the reply, the worst
case is a window rendering a change a few milliseconds early or late.

### Fan-out

`api_server/stream_registry.rs` holds one `mpsc` sender per attached client and copies each
message to all of them. It uses `try_send`: this is local IPC, so a client that cannot keep up
with a small buffer is broken rather than busy, and blocking on it would stall every other window
and back-pressure the brain. Such a connection is dropped, and the client recovers through the
reconnect path below.

## 3. Bootstrap and reconnect

A window reads its initial state once, through `ProtobufClient.bootstrap()` — the only place
bootstrap reads are issued.

**Every re-attach of the stream must re-run it.** Changes that happened while the stream was down
were pushed to nobody, and nothing replays them. There is no polling fallback to paper over the
gap. The first attach is exempt: it happens on the way to the caller's own bootstrap read.

## 4. Request/response conventions

RPCs keep their full responses on the wire. Scripts and integration tests
(`e2e_test/e2e_file_loop.sh`) drive the daemon purely request/response, and a partial or simulated
client must not have to be stream-aware to be useful. Read RPCs the Flutter app does not call are
part of that automation surface — they are not dead code.

The discard happens one layer up, in `ProtobufClient`:

- **Mutations return `Future<bool>`**, carrying only whether the service accepted the change.
  Transport errors still throw.
- **Reads return data**, and a read is free to have parameters — `PrepareLicenseCheck` takes a
  `force` flag and is still a read.

A mutation that genuinely needs its reply is the exception worth naming. With `GetSettings` split
out from `MutateSettings` and every create answered by its own `…Upserted` push, only the backup
RPCs read one. `BackupData` and `RestoreData` answer with an outcome, because the client's next
step depends on it: choosing a backup password, or asking for one. `VerifyBackupPassword`'s answer
is whether the password was right ([ADR-0012](adr/0012-password-encrypted-backups.md)).

## 5. Anti-corruption layers

Generated protobuf types never leak into domain logic on either side:

| Side | Mechanism |
|------|-----------|
| **Rust backend** | `domain_proto_conversion.rs` — `From`/`TryFrom` impls between `*Proto` types and domain models |
| **Dart frontend** | `Wire<T, M>` interface — `toWire()` / `fromProto()` on every model class, returning `Result<M, String>` |

Conversion failures throw. Client and service are generated from the same `.proto` and ship
together, so a row that will not convert is a bug in one of them, and skipping it would turn that
bug into a quietly shorter list.
